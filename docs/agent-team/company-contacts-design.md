# 组织与联系人 Agent 设计稿

日期：2026-10-22（Asia/Shanghai）。版本：V0.2，依据现有 Skill 全文及全部配套文件修订。状态：用户确认后已完成本地实现、离线验证及独立审查问题修复；实际验证范围见[验证记录](company-contacts-validation.md)。正文保留已批准的设计依据，实时接口仍以执行时说明为准。

## 1. 目标与用户已确认规则

接收一个批次的公司背调资料，使用 Apollo 调查公司人员与组织线索，自动选择合适联系人，通过 Apollo enrichment 获取工作邮箱。**完整使用 `D:/02钛白粉外贸/skills/research-company-contacts/` 这个 Skill 包**，以其中 `SKILL.md` 为业务入口，执行其全部适用阶段和报告规范，接续已开发的客户背调 Agent。Agent 负责批次组织和进度控制，单公司业务流程由该 Skill 统一维护。

用户已确认：

1. 自动选择联系人，无须用户审核候选名单。
2. 优先选择采购和管理角色；采购和管理都没有合适人选时，选择技术和销售角色。
3. 每家公司累计最多3位具名邮箱联系人，且本联系人流程内 Apollo 总消耗最多3 credits。公司查询、公司 enrichment、人员 enrichment、复验及收费重试均计入。
4. 先完成整批调查和选人，再按 Apollo 当前工具要求集中确认具体 enrichment 人数和费用；已有满足该要求的确认不重复询问。
5. 批次自动推进；邮箱获取不包含邮件起草、发送、序列或 CRM 写入。
6. 使用整个 `research-company-contacts` Skill，包括业务入口、报告规范和配套资源；不能只摘取其中的选人或 enrichment 片段另建一套简化流程。

此前“可以”确认业务方向，随后用户对本书面设计明确回复“同意”。两次确认均不代表批准尚未形成的真实人员名单或付费调用。下文的角色名、目录、状态和验收方式作为实施计划依据。

## 2. 角色、Skill 与执行方式

建议角色名 `company_contacts`，配置 `.codex/agents/company-contacts.toml`。

- 主 Agent：定位背调批次、明确执行范围、委派一个执行者、汇总交付及转达必要的工具费用确认。
- 组织与联系人 Agent：维护批次队列、公司预算、选人名单、调用记录、恢复进度和报告一致性。
- `research-company-contacts` Skill：完整承担单公司业务执行，包括§0名额与授权、§1对象与阶段、§2整体人员检索、§3组织结构、§4固定选人、§5工作邮箱获取、§6保存核对，以及“常见偏差”的处理要求。

采用项目角色与本地 Skill，不增加独立 API 应用。一个批次一个执行者，公司级串行处理，不嵌套派生；共享公司报告和预算台账也只允许一个写入者。由主 Agent 协调跨批次冲突，不能以不同批次目录绕过。

执行时优先使用界面实际可用的自定义角色；没有对应角色选项则传入 TOML 的完整 developer_instructions，并说明实际方式。无子 Agent 能力时由主 Agent 按相同规则执行。设计或查看角色不触发真实人员搜索或付费操作。

### 2.3 Agent 接收与返回的内容

主 Agent 委派时传入：背调批次及报告路径、公司范围和顺序、已有组织/邮箱资料定位、每公司3人和3 credits规则、本次选人优先级、已满足的具体工具确认记录（如有）、输出目录及恢复检查点（如有）。范围可从文件唯一确定时直接使用。

执行者返回：每家公司两份报告路径、组织调查范围和缺口、选定人员及实际邮箱结果、已消耗/预留/未知费用、批次进度和总结路径、待确认或受阻事项、准确继续位置。返回“阶段已保存”不能代替“邮箱已获取”。

## 3. 输入接收与复用

输入可以是客户背调批次目录、批次进度/总结文件，或用户明确指定的一组公司背调报告。读取批次索引和实际公司报告，核对客户ID、国家、主体、官网、背调日期、商业结论及公开联系人线索。

默认处理用户指定批次内的公司，按输入首次出现顺序去重；不自行只保留“继续开发”的公司。背调结论作为选人依据和限制保留，不自动变成联系人阶段的筛除规则。用户指定子集时只处理子集。

缺少可读背调时执行 Skill §1：先在明确的资料范围查找，确实缺失则记录缺口，并完成足以区分主体的最小官网核查。主体能够可靠确认时可继续本阶段，但明确没有完整背调；不能把缺报告直接当作公司已不合格。主体、国家或官网冲突仍未解决时保留为受阻项，不进入付费获取，其他公司继续。本阶段不重做完整 OGLD。

首次接收保存输入路径、文件指纹、公司ID、顺序与纳入依据。恢复发现输入变化时记录差异，不静默扩充队列。不同市场相同编号不自动合并；同一公司的品牌、域名别名和更名不重置名额或预算。

读取本任务已知的公司目录、市场索引及历史组织/邮箱报告；不扫描共享知识库或整个备份。旧报告可以复用，来源日期和原核验状态保留。历史具名工作邮箱计入3人上限，公共部门邮箱单列；已有3人或更多时停止新增，历史超限不删改成3人。旧邮箱不计为本轮新获取。

## 4. 两轮批次执行

### 第一轮：组织调查与自动选人

逐家公司执行：

1. 核对主体、历史报告、已有具名联系人、本流程已耗额度及待定费用。
2. 优先使用背调确认的域名和人员搜索，记录返回的组织信息及主体匹配限制。公司搜索或公司 enrichment 仅在确有必要时计划，不能为每家公司机械消耗1 credit。
3. 首轮不加职位筛选，按工具分页取回范围内记录，再补查采购、管理及其他关键职能缺口。保留查询条件、页码、总数、实际返回数、去重数和限制；接口可见记录不等于公司全体员工。
4. 整理主体关系、完整人员台账、职能分布，以及有直接证据的管理或汇报关系。职位归类不冒充官方部门，职位高低不证明汇报关系。
5. 自动选人，固定候选编号和原搜索人员ID，记录入选理由、未选原因、职责/现职疑点及预计费用。
6. 保存并回读组织结构和邮箱阶段报告，更新批次进度，再处理下一家公司。

首轮遇到需要确认的公司收费查询时，先保存待办并处理其他可独立执行的公司；汇总明确的查询范围和费用后，按对应工具要求办理。该确认可能先于人员 enrichment，不能承诺任何异常情形都只需一次确认，也不借改用另一工具规避确认。

### 第二轮：整批邮箱 enrichment

第一轮完成可执行的调查后，冻结实际选定人员、公司归属、每公司剩余名额和额度，查询 Profile 余额并汇总总人数与最大费用。无选中人员时直接交付实际调查结果，不发起空的付费确认。

先保存完整阶段文件和可审阅的费用清单，再请求一次整批人员 enrichment 确认。确认后按当前接口容量分组调用，不逐家公司重新审候选。当前 bulk 接口每次最多10人；各公司总消耗及整批批准范围都必须满足。

使用本会话人员搜索实际返回的ID；从搜索结果获取邮箱时每个 details 条目只传ID。关闭个人邮箱和电话揭示。按返回ID核对人、公司和域名，不按数组顺序映射。每次结果即时落盘，更新各公司两份报告和预算后继续。

## 5. 自动选人规则

第一优先组为采购和管理。制造企业的采购重点为原材料、供应链或相关采购职能；管理角色须与目标业务经营、工厂或采购决策有合理关联，不能只因职位高就优先无关人员。分销商、贸易商结合实际采购、产品及经营职责判断。

仅当采购和管理两类都没有合适人选时，启用技术和销售组。技术人员重点看产品评估或应用职责，销售可作为相关业务或转介入口，不能标成已确认采购决策人。

这里采用用户原话的严格口径：若第一组只找到1位或2位合适人选，就按实际人数交付，不用第二组自动补满3位。组内按职责相关性、目标主体归属、现职证据及独立联系价值排序，不预设采购与管理必须各占多少名额。

新增人数同时受历史名额、公司剩余额度、固定尝试范围约束。一般人员台账和备选名单可以超过3人，但不对全部人员 enrichment。选定后不因未匹配、无邮箱或失败自动无限换人；不足3人也是有效结果。

2026-10-22真实验证后的修正：先依岗位、公司归属和现职判断允许的岗位组，再从该组has_email=true者中排序并固定付费队列。false/未知只保留组织线索，不为补全遮挡姓名付费；采购/管理有合适人但无邮箱不触发技术/销售替补。分别统计相关候选、邮箱可用候选和固定付费人数，费用确认使用最后一项。

固定队列逐人保存布尔has_email:true及email_evidence原始搜索文件路径/SHA-256。检查器校验文件指纹和同一Apollo ID的true原值；false、未知、缺失证据或ID不符均拒绝。true不代表已经取得邮箱，也不保证具名工作地址或投递成功。每人保留一个首选工作邮箱；历史邮箱可直接复用，确需付费复验时同样执行邮箱准入。已发生的旧调用及扣费原样保留，新准入不追溯改写历史。

## 6. 每家公司3 credits的预算控制

按同一公司建立持久预算记录，批次引用该记录，不各自创建独立3-credit额度。定义本联系人流程的起点与已有消耗，历史任务中与本流程无关的旧消费单独记载，不混入当前流程或反过来当作当前零消耗证明。

每家公司记录：总上限3、已确认消耗、已预留费用、执行/扣费未知项、可用余额、对应动作和费用依据。恢复、换批次、改日期、域名别名或更名均不重置本流程额度；其他公司的余额不可调入。

调用前必须满足：已确认消耗＋尚未结算的最大预留费用＋本次最大费用≤3。当前人员 bulk enrichment 为每匹配人1 credit，未匹配0；成功匹配但无邮箱仍可能耗费1 credit。执行时重新读取工具说明，以当时价格及最大可能消耗为准，不把本稿价格永久硬编码。

例：公司查询已耗1 credit，则最多安排2 credits的后续动作；没有其他消耗时最多安排3人的标准工作邮箱 enrichment。复验不增加人数，但占费用。搜索返回空或未匹配只有依据实际工具结果才能记实际0，不从异常推断免费。

结果未知时保留最大预留，不盲目重试。先从已保存响应、请求状态或可归属的费用证据核对。账户余额变动可能来自其他任务，不能单凭余额差分配公司费用。批量结果不能可靠分摊时保留对应公司预留及未知状态，不能平均分摊或假填0。

余额或预算无法核清时暂停相关付费动作，其余已获授权且不受该不确定性影响的调查仍可继续。达到3 credits后交付已有结果和预算限制，不自行追加额度。

## 7. 工具确认与自动执行边界

业务上不设置选人审批。工具付费确认单独执行，保存确切名单、人数、最大费用、余额快照、确认记录与适用请求范围。批准范围内的分组执行不重复确认；换人、扩大范围或增加费用不能沿用旧确认。

2026-10-22读取的 Apollo bulk enrichment 对搜索后获取邮箱要求先确认全范围；适用原文为：

> Found [N] contacts. Enriching all will use up to [N] credits. You have [X] credits remaining. Want to proceed, or narrow the scope?

实际执行以真实选定人数N和已查询余额X替换，不使用示例值。“all”只表示本次固定选中的人员，不表示组织台账中的所有人员。工具当前还明确要求：

> Do NOT call this endpoint without explicit user approval.

本稿及用户给予的3-credit上限不冒充具体付费名单确认。已存在满足当前工具条件的具体确认时直接执行。工具规则若变化，执行者先核对再使用，不能臆测支持预授权。

## 8. 状态、保存和恢复

公司处理状态为 queued、in_progress、waiting_confirmation、completed、blocked；调查步骤与邮箱结果另列，避免“找到人”和“获取到邮箱”混为一项。

邮箱结果分别记录历史复用、本轮取得、匹配无邮箱、未匹配、无合适人选、名额已满、预算不足、失败、执行未知等真实情况。completed表示本次可执行范围已处理并保存，不保证有邮箱；等待确认、尚可恢复的必要工作或扣费未知不能标为整批成功。存在预算限制时明确“处理结束但邮箱目标有缺口”。

每次外部动作记录开始、返回/失败、目标公司、参数、分页或人员ID、请求ID字符串、原始返回位置及费用。日志不能代替工具调用，也不声称自动捕获全部调用。每家公司结束、整批待确认和暂停时更新正式报告、进度与内部检查点，不等到整批结束才首存。
