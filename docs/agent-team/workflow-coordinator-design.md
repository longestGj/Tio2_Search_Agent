# 统一调度 Agent 设计稿

日期：2026-10-22（Asia/Shanghai）。版本：设计稿 v0.1。状态：设计及[实施计划](workflow-coordinator-plan.md)均获用户同意，已进入本地实现与验证。下文保留设计时表述；实际实现、验证和限制以[使用说明](workflow-coordinator.md)及[验证记录](workflow-coordinator-validation.md)为准。

## 1. 用户目标与已确认边界

用户希望在当前项目中统一推进客户开发任务，默认终点为**开发信草稿完成**。

已确认的流程：市场搜集 → 客户背调 → 联系人与邮箱 → 开发信草稿。

已确认的职责：调度 Agent 只管理任务、进度、交接、阻塞和恢复。各专业 Agent 负责本阶段业务判断、质量检查及结论。调度 Agent 不重新评估公司资格、证据充分性、采购价值、联系人适合度、邮箱可信度或文案质量，不改写专业结论。

邮件发送的对接，等所有业务 Agent 开发完成以后另行讨论。本稿不设计发送阶段、发送队列、定时或30秒间隔接口。此处“草稿”指本地已保存的开发信成果，不代表向邮箱草稿箱写入。

本次授权是设计调度 Agent。设计文档不作为真实市场、背调、付费查询或邮件业务的执行指令。

## 2. 方案选择与首版规模

| 方案 | 特点 | 结论 |
| --- | --- | --- |
| 主对话临时安排各阶段 | 改动少，但跨会话难以准确恢复，任务范围和进度散落 | 保留为当前过渡方式 |
| 统一调度角色＋持久任务记录＋专业 Agent | 责任明确，能记录交接、恢复与重复请求，复用现有角色 | 本稿建议采用 |
| 专业 Agent 自行互派并同时推进多个阶段 | 可以提高吞吐，但容易形成多个调度者和交叉写入 | 首版不采用 |

建议角色名为 `workflow_coordinator`。运行于当前项目主对话，由主对话承载调度职责并委派专业子 Agent；专业 Agent 只处理本阶段，不嵌套派生或自行调用下一阶段。

首版一个工作流只派一个专业执行者，按阶段批次推进。一个阶段交回已保存的批次交接记录、且执行者结束或明确释放写入责任后，再派下一个阶段。某家公司受阻时，其余公司可由该阶段 Agent 按原有规则继续；批次交接时，只向下游传递专业 Agent 明确交出的公司。

多国家使用独立工作流目录。首版不建立一个后台进程自动轮询所有国家，也不在本轮设计中接管其他活跃对话。只有用户明确要求接续某工作流，且原执行者已释放责任时才转移。创建新对话、给另一个现有对话发送任务遵守对应用户授权；普通内部委派使用子 Agent。

## 3. 责任边界

| 事项 | 调度 Agent | 专业 Agent |
| --- | --- | --- |
| 明确本次国家、范围、终点、顺序和预算 | 记录并传递 | 在本阶段范围内执行 |
| 决定公司是否符合业务条件 | 记录来源结论，不再判断 | 按本阶段 Skill 判断 |
| 核对成果内容、来源和业务完整性 | 不复核正文、不运行第二套业务质量门槛 | 自检并承担本阶段成果责任 |
| 验证交接是否可接收 | 核对任务/公司ID、来源版本、必填交接字段、成果文件存在且可读取 | 保存成果并提供准确路径和版本 |
| 是否进入下一阶段或回到补核 | 执行专业 Agent 提交的去向，检查它属于本次任务允许的范围 | 提交明确去向、理由及恢复条件 |
| 专业结论冲突 | 暂停受影响交接，将冲突引用交回有职责的专业 Agent | 负责核对、澄清及修订自己的结论 |
| 任务进度、重复委派、写入归属、整体汇总 | 负责 | 提供真实阶段进度 |

交接检查的作用是确认“哪项任务、哪家公司、哪个版本、成果在哪里、下一步是什么”。文件存在或指纹匹配仅证明交接材料可定位，不证明研究质量。没有质量分数、调度审核通过/不通过等字段。

专业 Agent 的业务检查器留在其内部运行。调度 Agent 接收其自检记录引用，但不以自己解读检查器输出或报告正文为理由推翻专业决定。

## 4. 任务入口与范围

### 4.1 默认与明确指令

- “开发哥伦比亚市场”：建立全流程任务，默认目标为草稿完成。市场数量等缺失参数由市场阶段现有 SOP 处理，并在任务卡记录采用值。
- “秘鲁再找5家公司”：仍是市场搜集单阶段指令，不因存在调度 Agent 扩展为背调、邮箱获取或草稿任务。
- “对这份名单完成背调”：只执行指定背调范围。
- “这5家公司一直做到草稿”：显式冻结这5家公司，按流程推进。
- “继续”：恢复当前可唯一定位的任务；多项任务均可能对应时，整理已知进度后只询问必要的定位信息。

这些示例是入口设计，不表示已执行任务。用户可以指定更早的终点、排除公司、调整优先顺序或暂停。

### 4.2 工作流任务卡

至少记录工作流ID、国家、用户原始要求及日期、入口阶段、目标终点、公司范围表达、数量口径、来源路径、顺序、预算引用、当前负责人和实际能力清单。

“新增5家”与“累计65家”分开保存。市场总表即使包含65家，也只能把本次授权范围内的5家传给下游；已有池只是去重基线。若用户要求处理全部名单，则记录该明确范围。

市场搜集前不伪造公司ID，先记录范围表达；交接时，由市场 Agent 返回本次范围内的ID及各自结果，调度 Agent 冻结为下游队列。既有ID保留；按ID去重重复展示，遇到身份映射冲突交回市场 Agent，调度 Agent 不按名称或域名自行合并公司。

任务开始后名单新增、删除或结论变动，不自动扩大队列。记录版本变化、受影响ID及来源；同一授权范围内的补充交接可以续接，范围扩张由用户指令决定。全部变更保留历史，不能靠换任务编号重置额度或覆盖已完成记录。

## 5. 专业 Agent 的任务单与交接单

采用统一的调度交接外层结构，各专业 Agent 原有业务报告、状态和日志继续保留。该结构只负责记录与路由，不替代专业成果。

### 5.1 派发任务单

| 字段 | 含义 |
| --- | --- |
| workflow_id / assignment_id | 工作流与本次派发的唯一编号；调用前先保存 |
| stage / revision | 阶段及本次任务版本；业务阶段固定为market、research、contacts、draft |
| country / customer_ids | 国家和本次明确范围；市场初次发现尚无ID时使用任务卡范围表达 |
| source_artifacts | 实际输入路径、版本指纹及必要条目定位 |
| instructions_ref | 角色/Skill版本及完整任务要求；依现有项目方式加载完整角色 |
| budget_ref / authorization_ref | 本阶段预算、已有消耗和操作授权依据，未知项明确保留 |
| output_location / resume_ref | 成果位置和既有恢复检查点 |
| owner / allowed_routes | 当前执行者和本任务允许的下一阶段；防止交接自行扩大范围 |

### 5.2 交接单

| 字段 | 含义 |
| --- | --- |
| handoff_id / assignment_id / revision | 唯一交接编号，必须对应当前派发版本 |
| producer / stage / issued_at | 哪个专业 Agent、哪个阶段、何时交接 |
| batch_status / released | 阶段批次完成或阶段交付，以及是否已释放本次写入责任 |
| items | 公司级结果，包含客户ID、执行状态、专业结论原文及来源引用 |
| artifacts | 已保存成果的路径及版本指纹；需要多份成果时明确完整清单 |
| route / route_reason | 专业 Agent 提交的下一步：advance、revisit、hold、end或finish |
| next_stage / resume_condition | 明确接收方或恢复条件；补核还需具体未完成事项 |
| budget_used / uncertainty | 实际消耗和未知执行/费用等限制 |

每家公司分别给出去向，不能只用一个批次“完成”替代全部公司结果。运行中的进度通知不等于最终交接；首版只在 `released=true` 后派发后续工作。

专业结论引用在调度总表中保留原文和作者，不由调度 Agent改写为更乐观的判断。缺少去向时，请原专业 Agent补充交接信息，不自行从模糊报告推断。

对于已存在的旧报告，可以沿用专业 Agent已明确填写的结论字段进行固定映射；字段缺失、多义或互相矛盾，交回原阶段澄清。对旧成果的业务适用性和复用判断仍由接收它的专业 Agent负责。

## 6. 路由规则

| 交接去向 | 调度行为 |
| --- | --- |
| advance | 成果交接记录齐全、当前阶段释放写入责任且下一阶段在授权范围内时，加入下一阶段队列 |
| revisit | 记录负责补核的专业阶段、问题及恢复条件；有明确可执行新工作且预算允许才派发补核 |
| hold | 本公司暂缓，保留原结论及恢复条件；其他公司继续 |
| end | 本公司流程结束，保存专业 Agent给出的原因；不计为草稿完成 |
| finish | 仅在本任务目标阶段接受；默认是draft。记录草稿文件及专业 Agent声明的完成范围 |

与现有业务结果的衔接：

- 市场 Agent：在授权范围内，valid公司可交给research；其他四状态按市场 Agent明确去向保留待办或终止。市场未达到数量目标时，记录缺口；可交出的valid公司可以进入下游，未完成的市场工作仍在总表，不将全流程标记完成。
- 背调Agent（用户2026-10-22最终确认）：按objective-evidence-v1，完成且释放后的“继续开发”→advance/contacts，“排除开发”→end/null并保留客观依据；仅research终点两类均finish。旧四分类由生产者复核原证据后提供新判定，不自动映射。调度不判断证据质量。
- 联系人与邮箱 Agent：由该 Agent声明哪些公司/人员可交给draft、哪些受阻及原因。拿到邮箱的数量或一个verified标签，不由调度 Agent自行转化为写信许可；缺邮箱但能否形成合适草稿，也由专业 Agent按其规则明确交接。
- 撰写 Agent：声明本次草稿清单、对应客户/联系人ID和完成范围；调度 Agent核对所声明文件可读取，记录finish。尚缺必要输入时由撰写 Agent返回revisit/hold及具体原因。

没有质量投票、评分或由调度 Agent仲裁专业争议的环节。下游发现上游资料有疑问时提交具体ID和引用，由相关专业 Agent处理；相关公司的交接暂缓，其他公司继续。

### 补核循环的停止条件

同一公司、同一问题、同一输入版本和同一恢复条件，不重复派发相同任务。需要至少一项明确变化：新资料、工具恢复、增加的授权额度、用户要求的重新处理，或专业 Agent列出的尚未执行且当前可执行步骤。

背调Agent尚有必要调查未执行时保持in_progress/blocked并给具体恢复条件；充分执行后仍未知的信息保留为证据限制，不以“先补充核实”作为最终分流。重试与专业复核由背调Agent负责，调度只记录进度、防止重复派发。

## 7. 状态与完成口径

### 公司阶段执行状态

| 状态 | 含义 |
| --- | --- |
| waiting | 等待上游明确交接 |
| queued | 已具备派发条件，等待执行 |
| running | 已派发且有执行者负责 |
| completed | 本阶段已收到可接收的完成交接；业务去向单独记录 |
| blocked | 执行或交接受阻，有原因与恢复条件 |
| cancelled | 用户取消的范围，保留已有成果 |

专业 Agent原有五状态候选池、背调四状态和邮箱返回状态作为来源记录保留，不统一改造成上述调度状态。例如市场valid不等于整个开发任务completed。

交接还记录accepted/needs_correction/unknown三种技术接收结果。缺路径或ID不符时为needs_correction，保留专业 Agent提交的执行结果，不把“交接材料缺失”改写成“研究质量不合格”。无法确认是否成功派发时为unknown，不假定执行者从未开始。

### 公司流程结果与工作流状态

公司流程结果分别为active、draft_done、on_hold、ended、cancelled。草稿数和草稿完成公司数分别统计，一家公司多份草稿不增加公司数；公司所有已约定草稿是否完成，由撰写 Agent交接声明并列出对应文件。

工作流状态为running、paused、closed。仅在没有待执行任务且所有公司到达终点或被专业 Agent明确暂缓/终止/用户取消后，才可closed；还有等待恢复或未接入能力造成的blocked项时为paused或继续处理其他项。closed也不等于所有公司均有草稿，关闭原因和分项数字必须展示。用户可以明确关闭仍有阻塞的任务，保存未完成清单。

“全部目标完成”仅在用户数量/范围要求已满足，且范围内所有需要完成草稿的目标均由撰写 Agent声明finish后使用。存在暂缓、终止、取消或上游数量缺口时，按实际分项汇报，不用100%覆盖这些差异。零公司任务说明零结果原因，不生成“0/0全部完成”的结论。

## 8. 持久记录与写入责任

建议工作流目录：

```text
markets/<ISO2>/workflows/<ISO2>-WF-<YYYYMMDD>-<序号>/
  01_任务与进度.md
  02_交接与待办.md
  state.json
  events.jsonl
  assignments/<assignment_id>.json
  handoffs/<handoff_id>.json
  history/<时间与唯一后缀>/
```

专业成果继续放在现有prospecting、due-diligence、companies目录，联系人和草稿最终目录由各自角色设计确定。调度目录只存任务记录与成果引用，不复制一套公司事实或改写业务报告。

调度 Agent是state与调度events的唯一写入者。专业 Agent写自己的报告和任务专属交接文件；交接文件提交后保持原版，修订使用新handoff_id和更高版本，旧记录保留。

state是当前进度快照；events为带连续序号的追加事件，保存足以恢复该快照的任务变更。计划的保存顺序是先追加并落盘事件，再以临时文件替换state，最后同步两份正式进度文档。若任一步失败，暂停新派发；恢复时从最后有效事件修复快照与文档，不重做已执行的业务动作。损坏记录先保全，不静默删除。

实施时需要工作流写入锁及项目范围的资源占用记录：至少覆盖国家候选池、阶段批次和公司报告路径。资源认领由一个受锁保护的记录操作完成，不能先检查空闲、再无保护地写入。并行工作流也要检查同一公司资源。

锁或执行者状态未知时，不能凭“很久没有更新”抢占；先确认原执行者结束或已交接，再接续。未使用统一调度的既有任务不自动出现在资源表，发现这些任务正在写入时先协调责任，不声称新机制能控制所有旧任务。

## 9. 派发、恢复与错误处理

1. 读取任务卡、最新记录和能力清单，确定原任务范围与恢复位置。
2. 确认写入归属，核对当前活跃执行者、来源版本及未解决的派发未知项。
3. 按阶段顺序选择queued任务；能力未接入时标blocked/dependency_unavailable，保留草稿目标。
4. 调用前持久保存assignment_id与派发意图；成功后记录真实执行者引用。调用超时但结果未知时不自动再派，先查执行者或本地交接文件。
5. 接收进度通知，仅更新执行进度。接收最终交接时核对任务ID、版本、公司范围、路径和枚举字段，再按固定路由登记下一步。
6. 同一handoff_id重复到达只接收一次；旧派发版本迟到的结果单列历史，不覆盖当前版本，不触发第二次下游任务。
7. 单公司阻塞按原规则保留，其他可执行项继续；工作流记录能力、公共工具或总预算限制阻止执行时暂停相应范围。
8. 保存正式进度与待办，报告下一步；结束对话后不声称调度 Agent持续在后台运行。后续由用户续接，或另行设计并获得授权的执行机制恢复。

已有完整成果能否直接复用由所属专业 Agent判定。调度 Agent识别同一已接收任务、同一版本和同一交接，避免重复派发；对跨批次旧成果只传递引用，不自行判定仍适用。

来源文件意外改变时，记录受影响任务并请求生产者补充变更交接。冻结队列不自动增删，下游是否需要重做由负责的专业 Agent说明；调度 Agent按明确决定建立新版本任务，不覆盖旧完成记录。

## 10. 预算、操作授权与任务终点

预算按阶段记录单位、上限、已用、未知及来源。沿用阶段已有规则：市场搜集使用其SOP预算；背调预算独立，未设置时记录未设硬性上限；联系人付费与额度按实际工具约束和已有授权处理。调度 Agent不能把市场的剩余查询额度当成其他阶段的授权，也不能把不同单位相加成一个“剩余预算”。

用户设置整体上限时，调度 Agent在其范围内分配阶段额度，并保留尚未分配量；阶段派发和恢复不得扩大整体上限。不能确定的消耗保持unknown，暂停可能超出额度的派发并交给执行者对账，不用0代替未知。

专业 Agent遇到当前工具强制要求的确认时，向调度 Agent提交已确定的对象、人数、费用及工具要求，调度 Agent集中转交用户；已有满足要求的授权不重复询问。此机制不额外建立调度质量审批。

默认草稿终点作为任务卡字段固定，后续专业 Agent不能自行改成外部发送。发送接入是以后单独设计的事项，本稿没有待实现的发送占位任务。

## 11. 现有组件如何接入

| 阶段 | 当前实际基础 | 本方案需要的适配 |
| --- | --- | --- |
| market | [市场角色](../../.codex/agents/market-research.toml)、四报告、日志及检查点 | 交出本次授权范围内ID、各公司去向、四报告版本及是否释放执行责任；保留原核验规则 |
| research | [背调角色](../../.codex/agents/customer-research.toml)、公司报告、批次进度及checkpoint | 接收明确公司范围，输出已有四类行动结论的固定路由及恢复条件；保留原业务检查 |
| contacts | 已有[联系人Skill](../../skills/research-company-contacts/SKILL.md)，尚无独立Agent | 后续角色开发时实现任务/交接契约，承担选人、累计名额和邮箱判断；目前标未接入 |
| draft | 尚无专用撰写Agent | 后续角色开发时定义草稿交付标准及目录，实现相同交接契约；目前标未接入 |

首版可以验证market与research的真实接续；contacts与draft先用明确标注的模拟交接验证调度行为。缺少专业 Agent不能用主调度直接开展专业业务来填补，也不能把背调完成标成草稿完成。

建议实施文件位置为`.codex/agents/workflow-coordinator.toml`，以及项目`skills/coordinate-prospecting-workflow/`的调度规范、模板和必要记录工具。这些路径是未来实现建议，本次不创建可执行角色或Skill。原有专业 Agent只增加必要的输入/交接说明，不改变业务标准。

## 12. 设计验收场景

以下为未来实现的验收要求，当前未执行，示例均为虚构情境。

1. 给出完整开发任务，默认终点为本地草稿；明确只搜集或只背调时不扩展阶段。
2. 累计65家名单中本次只授权新增5家，下游队列仅含这5家。
3. 已完成且释放的背调中，有明确客观排除依据的结束下游，其余进入联系人及草稿；旧四分类先由背调生产者复核，原证据和未知保留，调度不审业务质量。
4. 专业 Agent给出同一结论但证据长短不同，调度动作相同；调度 Agent不打开外部网站重验、不按正文打分。
5. 某公司hold，其他公司继续；最终分别显示草稿完成、暂缓、终止和未完成数量。
6. 交接文件缺失、ID不符或旧版本迟到，只阻止该项交接并请求修正；不更改业务结论。
7. 相同handoff重复提交不重复派发；派发后回执丢失先定位原执行者，不重建任务。
8. 报告已保存而调度进度落后，从已有有效交接恢复；events已写而state未写时重建快照，不重复调查或付费。
9. 同公司两个工作流竞争写入时只允许一个认领；仍有活跃执行者时不能抢锁。
10. 无新条件的同问题补核不循环派发；工具恢复或明确新资料到来才续接相应任务。
11. contacts/draft尚未接入时准确暂停相应公司，仍保留草稿目标，不虚报流程完成。
12. 来源更新不扩大授权公司范围；消费者提出业务疑问时由专业 Agent处理，调度只记录路由。
13. 预算未知/耗尽保留并阻止受限动作；重新开始会话不重置额度。
14. 撰写 Agent声明一家公司的多份草稿完成，按文件清单登记多份草稿、一个完成公司；缺文件请求补交。
15. 市场数量目标未满足但已有公司完成草稿，报告两项独立进度，不声称原数量目标已完成。
16. 用户暂停、取消或缩小范围时，停止新派发，向当前执行者传达变更并保留实际已完成动作；无后台运行能力时不承诺持续执行。

首轮可用3家虚构公司：一家推进至模拟草稿完成、一家背调后明确暂缓、一家因下游能力缺失受阻。调度结果应分别统计为1家草稿完成、1家暂缓、1家未完成。真实业务验证在实现后使用另行明确的范围，不能把模拟文案写成真实开发信。
