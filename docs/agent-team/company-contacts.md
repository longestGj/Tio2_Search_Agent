# 组织与联系人 Agent

角色：`company_contacts`。完整使用 [research-company-contacts](../../skills/research-company-contacts/SKILL.md)，包括全流程、完整两报告规范及本地批次补充。

## 使用

在本项目中指定一份背调批次，例如：

> 使用组织与联系人 Agent，处理指定背调批次中的公司，自动选择采购和管理人员，两类均无合适人选时选择技术和销售。沿用已有联系人，每家公司最多3位联系人和3 credits。

> 继续上一批组织与联系人工作，先核对保存的报告和公司账本，不重置预算，不重复获取。

示例不是已经执行的任务。目录/名单可唯一定位时直接处理，否则只澄清必要输入；单公司任务不会扩充为整个市场。

## 默认行为

第一轮逐家完成主体、完整人员检索、组织与职能整理、自动选人及阶段保存；第二轮汇总全批人数和费用，在Apollo工具要求的具体确认满足后分组获取工作邮箱。候选无需逐人审批，工具确认只针对固定范围，满足后不重复请求。

第一组采购/管理只有1—2位时按实际人数交付，不用技术/销售补满。管理职位不代表采购权。组织台账保存检索范围内所有人员；3人仅限制具名邮箱联系人。旧邮箱占名额，复验计费；公司查询等其他Apollo费用同样计入3 credits。未知扣费保留预留，不盲目重试。

流程V1.3：付费队列只选择上述合适岗位组中原始搜索has_email=true的人，false/未知保留为组织线索。采购/管理有合适人但无邮箱，不因此跨组补人。相关候选数、邮箱可用候选数和固定付费人数分别交付，费用确认只计最后一类。检查器核对has_email布尔值、原始搜索文件指纹及相同人员ID；历史邮箱免费复用，付费复验适用同一条件。

公司报告和 `contacts/ledger.json` 位于 `markets/<ISO2>/companies/` 的同一公司目录。批次为 `markets/<ISO2>/contacts/<批次ID>/`，交付两份正式批次Markdown及恢复日志。公司账本跨批次沿用，旧来源日期不改成本次核验日期。

## 检查和实际能力

```powershell
python -X utf8 skills/research-company-contacts/scripts/check_batch.py --batch "<实际批次目录>"
python -X utf8 skills/research-company-contacts/scripts/test_check_batch.py
```

检查器0=登记结构一致，1=错误，2=未知/未闭合/需对账；等待工具确认即使0也不是全部完成。预调用检查在预留和begin之前执行；一旦begin已保存而未取得返回，只能核实原动作，不能拿检查结果推动重复调用。

检查器不联网、不修改文件、不判断事实真实性或用户确认真伪，不拦截未登记调用，也不加并发锁。按名称自动发现角色取决于实际客户端：若无company_contacts选项，主Agent读取完整TOML委派给专门执行者；没有子Agent能力则按相同规则主Agent执行并说明。

开发验证与尚未验证事项见[验证记录](company-contacts-validation.md)。V1.2已完成一次秘鲁真实查询及15人获取；V1.3经离线回归后，已对另外5家秘鲁公司真实测试，仅1位true候选付费并取得邮箱，实际1 credit。邮箱准入有效，但结果日志的历史错误事件导致最终检查未通过，不能称整个流程全部通过。原批次报告及15 credits消耗保留，新检查器可能拒绝旧选择数据；不得伪填字段或删改旧账本来通过检查。
