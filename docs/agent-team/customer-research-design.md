# 客户背调 Agent 设计稿

日期：2026-10-22（Asia/Shanghai）。状态：用户已确认；随后授权全量同步 GitHub 并开发，实施见 [计划与记录](customer-research-plan.md)。

## 1. 用户目标与已确认决定

在当前 Codex 项目中增加客户背调 Agent，输入为某个市场的市场搜集 Agent 成果物，复用 GitHub 上现有客户背调 Skill，自动逐家处理整份名单。完成一家并保存后继续下一家，不逐家要求用户说“下一家”。已有背调优先复用，不默认重做。

本稿将上述决定具体化。下文关于目录、队列字段、复用检查、异常处理和验证案例，是建议采用的实现设计，不表示已经配置、验证或执行了真实背调。

## 2. 角色与 Skill 分工

建议角色名为 `customer_research`，配置文件为 `.codex/agents/customer-research.toml`。

- 主 Agent：识别背调任务、确定输入名单和范围、委派给一个专门执行者、汇总交付。
- 客户背调 Agent：管理批次、读取名单与历史报告、逐家调用背调 Skill、检查成果、保存进度、恢复中断。
- `research-customer-ogld` Skill：负责单家公司 OGLD 调查、证据判断、商业结论及固定报告结构。完整完成一家后进入下一家。

采用当前项目“角色配置＋本地业务 Skill”方式，不增加独立 API 应用。每个批次一个执行者，不嵌套派生，不同时处理多家公司。原 Skill 允许的同一公司独立来源读取，不改变公司级串行顺序。

设计、查看或修改本角色，不触发真实背调。正式调用时，按界面实际能力使用自定义角色；无法按角色名选择时，主 Agent 将完整角色指令和任务交给专门子 Agent，并如实说明。不能创建子 Agent 时按同一规则由主 Agent 执行。

## 4. 输入与队列

### 输入定位

用户可以提供候选总表路径、市场批次目录，或在上下文中指定某个市场的明确成果。执行者读取总表及可定位的配套证据、复核说明和检查点。

仅说市场名时先读取该市场索引及实际成果；不能唯一确定目标名单才询问。不能仅依文件名日期选取未交付目录，不能把不同批次直接拼接相加。

### 默认范围

- 默认处理指定名单中所有唯一 `valid` 公司；其余状态在接收记录中列出及说明未纳入原因，不静默丢弃。
- 用户明确指定其他公司时单列授权范围，先处理主体定位，不将其伪装成市场阶段已核验。
- 沿用 `candidate_id`／客户 ID，保留 `lead_id`、原批次、来源文件及条目定位。客户 ID 按市场识别，不因跨国家编号相同合并。
- 同一公司在总表正文、单条核验记录、历史继承段重复出现时只建一个队列项；品牌、集团和法人以证据归并，不能仅因共享域名合并。
- 按输入有效名单的首次出现顺序执行；用户指定顺序时沿用。不得为了先做容易的公司而自行更换顺序。
- 开始时保存本批输入范围、文件指纹、纳入 ID 和顺序。输入后续发生变化时记录差异，不在运行中无声扩充或删减队列。

### 队列字段

每家公司至少记录：客户 ID、公司名、国家、输入来源、顺序、处理状态、处理方式、原报告路径与日期、本次报告路径、当前 OGLD 步骤、已完成动作、剩余工作、阻塞原因、行动结论和最后更新时间。

处理状态与处理方式分开：

| 处理状态 | 定义 |
| --- | --- |
| queued | 已纳入，尚未开始处理 |
| in_progress | 正在核对历史成果或执行背调 |
| completed | 复用或新增成果已经检查，报告可读，批次记录已保存 |
| blocked | 有明确限制使本次处理无法完成，保留恢复条件及已取得证据 |

处理方式为 `reused`（直接复用）、`supplemented`（复用并补核）或 `new`（新背调）；未判定时留作未判定，不提前写成复用成功。商业行动结论单独采用 Skill 的“继续开发／先补充核实／暂缓开发／不匹配当前产品”。

## 5. 复用已有背调

先在指定公司目录、市场成果索引以及本任务已知报告位置定位历史背调。匹配客户 ID、国家、主体、域名及必要的注册或地址信息；同名或相似文件名不能作为充分依据。不自动扫描备份或其他项目。

| 历史成果情况 | 处理 |
| --- | --- |
| 同一主体，八节及证据目录可用，无已知重大冲突，本次未要求更新 | 直接复用；保留原报告和调查日期，在批次记录注明本次仅做资料检查、未重新联网核验 |
| 同一主体，报告缺章节、关键来源定位或存在影响判断的缺口 | 保留可用内容，定向补核缺口；不得用“复用”跳过 Skill 的交付要求 |
| 已有新证据与原报告的主体、业务、官网或关键结论冲突 | 复核有关事项，保留双方证据与结论变更，按实际结果更新 |
| 仅有部分调查或中断草稿 | 从实际进度续接，不把草稿当作已完成背调 |
| 找不到报告，或确认不是同一主体 | 新建本公司的背调，不移用其他公司的结论 |

不设置未经用户要求的固定过期天数，不仅因日期较早就整份重做。历史现职、登记状态、采购记录和技术文件不得改写成本次已验证；本次确需判断当前情况时，针对该事项核实。

继承报告中的“未知”本身不要求无限补查。如果原报告已记录规定调查及限制，且本次没有新的补查条件，可以保留。结构完整与事实全部查明是不同结果。

直接复用时不改原文。需要补核更新时，先保存历史快照，更新同一报告文件并保留原调查日期，新增本次更新日期、补核范围和变更说明。不因为文件名含旧日期而新建第二份互相竞争的当前报告。已有多个版本时先核对版本关系，无法确定时保留冲突，不猜测哪个最新。

## 6. 逐家执行及完成标准

1. 读取批次进度和当前公司资料，核对唯一主体及复用条件。
2. 可直接复用则检查报告与来源定位，登记复用范围；需补核或新建则读取 Skill、完整 SOP 和报告模板后执行。
3. 按 O → G → L → D 获取证据，做商业判断，保留逐项来源、日期、性质及限制。
4. 按模板复核，保存并回读报告，核对客户 ID、八节、官网表、关键结论、来源目录及本次执行边界。
5. 更新进度及报告链接后处理下一家公司，不增加逐家确认节点。

某个维度访问受限时，记录实际尝试、替代路径和限制。若按 Skill 已完成可执行的调查，报告可带缺口交付并标为 completed；若还有因预算、工具中断等未能执行的必要工作，则标为 blocked。不得在新报告里将整段“未执行”当作完整背调，或以占位报告计为完成。

单公司受阻时保存阶段成果和恢复条件，然后处理下一家；整体工具或保存能力不可用时暂停整批。所有公司均 completed 才称“整批处理完成”；存在 blocked 时称“阶段交付，仍有 X 家未完成”。直接复用数、本次补核数和新背调数分别报告，不能声称全名单重新联网核验。

## 7. 记录、预算与恢复

### 执行记录

为本阶段定义独立的批次进度和动作记录，不直接套用市场搜集脚本的五状态、发现门槛或查询预算。首版只要求轻量本地记录与检查，不因已有脚本而复制不适用的业务状态机。

每次搜索、页面读取、失败、重试和替代查询，记录客户 ID、维度、实际工具、目标、开始记录、返回结果、证据定位及执行是否确定。返回后及时保存，再继续下一动作。独立请求即使同次工具调用也分清实际查询和读取目标。

中断留下未闭合动作时，先查已保留返回：可确认则据实补记；无法确认则保留“执行未知”，新重试另记，不伪造过去时间或调用次数。调用开始记录不证明实际执行。日志不能自动证明已捕获所有工具调用，仍需与可取得的调用历史核对。

### 预算与停止

整份名单是业务范围，不继承市场搜集的查询次数或时长预算。用户设定的本批上限优先，恢复时沿用已消耗量，不因换会话重置。未指定数值上限时明确记录“用户未设硬性上限”，按 SOP 有限尝试，完成检查与保存后继续下一家，不无限重复相同失败查询。

同一入口首次失败后优先尝试实质不同且可用的来源；无新线索、不存在可执行替代路径时记录具体缺口，不靠重复刷新延长调查。是否交付带限制报告或标为 blocked，依第 6 节判断。

任何实际付费、额度消耗或外部写入按当时工具说明及用户授权处理。某项操作缺少必要授权时登记为限制，不推断整批授权包含费用；其余可独立进行的公开背调继续。

### 恢复

每家公司完成、受阻及整批暂停时保存：固定输入队列、采用 Skill 版本、状态统计、当前公司及步骤、报告版本、已用预算或未记录项、未闭合动作、剩余工作、下一家公司和暂停原因。

恢复先核对最后完整检查点及实际报告，修正“报告已保存但进度尚未更新”等不一致；不依赖对话记忆从头执行。优先恢复当前中断公司；只有明确阻塞记录允许跳过到下一家。已完成复用项不重复处理，blocked 项在恢复条件满足后续接。

同一批次以及共享的公司报告均只有一个写入者。其他批次正在处理同一公司时交由主 Agent 协调，不能仅因批次目录不同就并行覆盖报告。

## 8. 本地交付结构

沿用已有市场和公司目录。新公司建议按客户 ID 建目录，已有公司目录保留原名，以 ID 映射定位。

```text
markets/<ISO2>/
  companies/<已有公司目录或客户ID>/
    <公司名>_背调报告_<首次调查日期>.md
    history/<更新时间与唯一后缀>/
  due-diligence/<ISO2>-DD-<YYYYMMDD>-<递增序号>/
    01_批次进度.md
    02_批次总结.md
    logs/
```

日期使用北京时间，新建批次检查序号冲突；续接未完成批次沿用目录。`01` 记录任务输入、版本、队列及恢复点；`02` 记录实际成果、复用/补核/新增数量、四类商业结论、受阻项、验证范围及全部公司报告链接。开始时可先建真实进度，不能预先写出成功总结；暂停交付的总结须准确说明阶段状态。

上游市场搜集四文件保持原记录。背调发现主体冲突或不匹配时在本阶段记录并指出需回查的候选 ID，不自动改写上游 valid、删除公司或把背调结论套用成上游状态。

## 9. 后续业务边界

执行 Skill 内的公开联系人线索研究和已有资料整理。选人时遵循项目按公司类型及实际职责判断的规则，不仅因职位高而认定采购权；保留事实、推断及未知。

本阶段不自动进入独立的组织架构整理、Apollo 人员或邮箱 enrichment、开发信、发送及 CRM 写入流程。每家公司优选联系人最多三人的已确认约束继续适用；人员资料与优选联系人不混为同一计数。取得公开邮箱也不代表邮箱可投递、已联系或获准发信。

本项目的当前用户授权及 AGENTS.md 优先于 GitHub Skill 中的历史后续审批表述。源 Skill 关于“获取个人邮箱前展示候选人”的指令留在后续联系人阶段核对，不据此给本批公开背调增加逐家审批。

## 10. 实施范围与验收

设计确认后的预计文件范围：新增角色 TOML、导入 GitHub Skill 及必要配套资源、增加本地批次规范与模板、更新项目 AGENTS.md/README、增加角色使用说明和验证记录。是否需要轻量校验脚本，在实施计划中依可检验要求确定，不扩建通用调度平台。

实施验收至少包括：

1. 角色可解析，引用文件存在，导入来源和本地修改清楚可追溯。
2. 一份同时包含五状态、重复展示和继承记录的模拟名单，纳入数量和 ID 正确。
3. 已有完整报告直接复用，原内容和原核验日期不变；仅补核项记录本次新证据。
4. 同名不同主体、同集团不同主体及共享域名不被错误复用。
5. 缺章节、失效来源、重大新矛盾与历史未解决项按规则分别处理。
6. 完成一家并保存后自动处理下一家；单公司受阻能继续其他公司且不虚报整批完成。
7. 中断、预算耗尽、未闭合动作、报告与进度不同步时正确恢复，不重置预算或重复执行已完成项。
8. 固定八节、官网表、来源映射、商业结论、复用统计和报告链接一致。
9. 上游名单未改写；没有自动获取邮箱、发信或向外部系统写入。

验证报告分开陈述文件检查、离线场景验证与真实联网试跑。本次设计未进行真实背调；后续真实试跑须使用明确的公司范围和任务授权，不因设计确认自动处理整个市场。
