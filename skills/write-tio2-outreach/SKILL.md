# MYtio2 开发信写作

把背调、组织及联系人资料和产品证据转成针对具体收件人的英文草稿，保存完整内容及逐封状态。业务基准为项目Mail Group SOP V1.2；项目本地版为1.6。每封提供一项与收件人职责相关的具体价值。

## 面向专业人士写作

正文直接提供与客户有关的具体事实、我方产品／资料／支持和一个明确CTA。通过这些内容体现价值，不向客户解释“先看技术资料再决定测试”等行业常规，也不另加说明这些内容为什么有价值的流程句。问题识别、岗位分析与价值判断放在内部输入卡，不逐项翻译成正文句子；没有已证实问题时，不用通用评估议题填空。客户主动提问或产品有必要说明的具体条件时，准确回答，保留典型值、范围等影响理解的限定。CTA可简短交代请求内容及目的，正文不重复它的理由。逐句检查信息增量与重复，不为凑字数加句。

## 开始与恢复

1. 每次开始/恢复，全文读取[项目Mail Group SOP V1.2](../../sops/MYtio2_开发信编写SOP_Mail_Group_v1.2_审查稿.md)，不得只凭本入口、历史样稿或对话摘要写作。这是当前唯一业务SOP正文；文件名保留“审查稿”以维持既有链接，2026-10-22用户已授权接入执行。`references/mail-group-sop-v1.1.md`只用于上游来源追溯，不作为当前写作规则。
2. 读取[本地执行与保存规范](references/local-execution.md)，按[草稿模板](assets/draft-template.md)建稿。批次任务同时读取[批次模板](assets/batch-templates.md)。用户本次具体要求优先，项目已确认默认值见本地规范。
3. 读取指定公司当前背调、组织/邮箱报告、旧稿、可获得的真实沟通记录和产品资料。建立SOP§3输入卡，按§4确认岗位与写法；保留来源ID、完整网址、日期、文件版本及冲突。不把已获取邮箱的所有人员自动列为收件人。

按用户2026-10-22最终背调规则，流程衔接只承接已完成且释放的“继续开发”；有客观证据的“排除开发”保留理由，不进入写作。旧“先补充核实／暂缓开发／不匹配当前产品”交背调生产者复核并提供新判定，不由写作角色重做背调筛选。保留客观证据及未知，不宣称已证实需求、购买意愿或技术适配。用户单独授权的写作任务依明确范围执行；缺失收件人、应用或技术资料按既有规则记录具体待办，不伪造事实。固定产品对应表与本地草稿终点继续适用。

## 批次前卖方资料核对

批次开始先完整读取sops/MYtio2_卖方资料与签名确认.md，一次核对本次拟用身份、签名、产品资料和附件版本，保存引用与本批差异；已确认且适用的事项在全批复用，不逐公司重复询问。Mail 1与Mail 2缺口分别判断，不将已确认的签名问题继续挂起。

## 同公司合写

默认同公司本次已选联系人共用一封，按阶段准备Mail 1和Mail 2，共两封；仅用户明确要求分写时拆分。To列已选收件人，称呼覆盖各人；综合岗位选择共同联系理由与一个CTA，不将个人稿拼接、不新增收件人或自动抄送。真实回复沿用实际沟通范围。

## 写作与复核

按SOP§3–4读取资料并判断岗位，依据实际沟通选择§5–7的Mail 1–4或直接回复。每封只围绕一个联系理由和一个主要CTA；客户已有问题时先回答，不机械走四封顺序。

| 场景 | 关键处理 |
| --- | --- |
| Mail 1 | 具体客户事实→相关产品／资料／支持→一个明确CTA；问题与岗位价值在内部判断，不硬补问题句或流程解释；无附件；见SOP§5 |
| Mail 2 | 使用SOP§6“用户确认的第二封模板”：产品／TDS→REACH资料表述→附件说明→1 kg免费样品→样品CTA；按固定牌号及真实TDS替换技术段；正文≤90词 |
| Mail 3 | 承接真实回复推进测试；1 kg免费样品已确认，运输与日期按实际条件处理 |
| Mail 4／回复 | 按测试反馈、报价、暂缓或真实未回复状态处理；停止联系/拒绝/退信先暂停 |

新建开发信主题突出Malaysia并体现产品或应用；真实回复保持原线程主题。固定From/Reply-To为`ai-long@mytio2.com`，署名Ai Long，每封使用一次SOP§8完整签名。签名中的品牌/资质文字不扩大为具体牌号、批货或进口主体的覆盖承诺。

拟用事实、牌号、参数、供货条件分别追溯证据。只有旧网页而无TDS时，Mail 2为待技术资料复核的内部候选稿；Mail 1可独立完成。不得以已确认设计、旧推荐或“verified”替代产品适配、现职或投递证据。

附件按SOP§8逐项登记原文件、版本、用途、适用主体/市场和可分享状态。草稿阶段记“计划附加”或“文件已核对”，不记“已附加”。Mail 2按用户确认模板可预写“I've attached”，但预备稿须标“待核实并实际附加后使用”，资料缺口保留；正式发件前必须核实文件并实际附加，不能据模板将附件状态登记为已附加。未查阅往来时记“沟通历史未核实”，正文不虚构此前发送、对话、回复或测试同意。

逐封按SOP§9先审核客户价值、岗位针对性及CTA，逐句删除无新增信息的常识、流程解释及重复理由，再审核事实与格式；具体资料不足按§6保留待办，不将整组标为已复核。使用`scripts/count_words.py`核对词数，保存后回读。词数通过仅证明计数条件，不证明事实、附件适用性、文案质量或发送许可。

## 交付

按SOP§10逐封交付。每封交付完整英文稿（From、Reply-To、To、Subject、称呼、正文、落款、完整签名）、内部写作摘要、附件清单、两类词数、证据和待办。内容、发送、跟进三类状态分别登记；未查邮箱不写“没有回复”。以保存成功的Markdown文件及可打开链接为交付依据。

收到用户修改意见时，先将反馈与影响范围保存到草稿、批次报告和检查点；尚未修订的稿件标“需重写”，user_review记“需修改”，不继续当作完成成果。修订后完成复核，再将新版本记为“未审阅”，保留旧反馈和版本。

本Skill只起草/修订/审阅并本地保存。SOP的发送规则用于后续交接，不是当前发送授权。用户明确另行要求发送时，携带其既有授权、确定的收件人/正文/附件交给适用邮箱流程；当前环境未有该流程时如实说明，不因SOP提到`send-mytio2-email`就假定已安装。保持当前任务终点，不自动查联系人、付费补邮箱、建序列、排期、写CRM或上传。
