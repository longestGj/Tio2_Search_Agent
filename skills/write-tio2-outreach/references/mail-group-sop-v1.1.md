## 1. 目的与适用范围

将客户背调、组织结构、联系人信息和产品资料，转化为针对具体收件人的英文开发信。每封邮件解决一个沟通问题，逐步推进供应商认知、技术评估、样品测试与合作。

本版以已经使用的英国市场流程为基础。用于其他市场时，先核实当地业务、语言和资料适用性，不直接沿用英国进口主体或合规覆盖结论。

流程顺序：**读取资料 → 确定对象与阶段 → 确定联系理由和产品依据 → 起草 → 复核 → 保存文件 → 按明确发送指令交接。**

客户已有具体询盘或回复时，优先回答实际问题，不机械套用四封顺序。写作、获取邮箱和实际发送分别记录；起草任务本身不触发发送。

## 3. 写作前：建立收件人输入卡

先读取以下文件的当前版本：客户背调报告、组织结构文件、联系人邮箱文件、此前开发信和可获得的真实沟通记录、拟用产品的 TDS 与支持资料。不能仅凭旧对话摘要重建已保存正文。

| 输入字段 | 必须记录的内容 |
| --- | --- |
| 客户 | 客户 ID、名称、法定主体或商号、国家、经确认的官网、背调版本及日期 |
| 联系人 | 姓名、原始职位、公司、职责相关性；职位冲突和未核实事项 |
| 联系渠道 | 工作邮箱、来源、获取或验证日期、平台状态、catch-all 标记；未知项如实记录 |
| 具体业务 | 生产商／分销商等角色、具体产品或应用；TiO₂ 使用属于已确认、企业自述还是分析推断 |
| 拟引用事实 | 具体事实、证据 ID、完整来源网址、资料日期或核实日期 |
| 产品依据 | 用户指定或拟推荐牌号、TDS 文件名与版本、拟引用应用或参数、尚需验证的条件 |
| 沟通进度 | 首次接触／跟进、此前实际发送日期、客户实际回复、已承诺事项、当前阶段 |
| 本封目标 | 一项主要 CTA、拟用附件、当前可确认的供货或样品支持 |

如果无法读取历史发送或回复记录，标为“沟通历史未核实”，不用 “as discussed”“following our conversation”等句式假定此前联系。

### 根据岗位选择切入点

| 对象 | 主要关注点 | 不应自行认定的事项 |
| --- | --- | --- |
| 采购 | 原料采购入口、供应商评估流程、已确认的供货条件 | 有采购职位就一定负责 TiO₂ 或拥有最终批准权 |
| 技术／研发 | 应用体系、TDS、评估参数和测试条件 | 技术支持、培训或技术销售就是配方研发负责人 |
| 管理层／运营 | 业务关联、工厂范围、内部转介 | 董事或总经理直接负责原料采购 |
| 分销商 | 服务的下游应用、产品组合、技术支持需求 | 分销商自己拥有工厂、直接使用 TiO₂ |

优先使用已确定的工作邮箱。需要公共入口转介时，使用已核实的官方渠道并匹配部门称呼，不猜测个人邮箱。

## 4. 六步起草流程

1. **核对主体和联系人。** 确认所写业务属于目标公司，区分集团、英国法人、工厂、品牌和分销商；关键身份冲突未解决时仅作内部草稿。
2. **确定邮件阶段。** 按实际沟通选择 Mail 1–4 或直接回复。用户要求 Mail 1 和 Mail 2 时，一次起草两封；其他阶段按需求处理。
3. **选一个联系理由。** 优先使用具体产品、工艺或公开生产业务。企业自述用 “Your website lists…” 等方式归因，不把未知采购量、现用供应商或客户痛点写成事实。
4. **形成产品匹配依据。** 按“客户具体应用 → 待满足的要求 → TDS 或测试依据 → 需要客户评估的条件”建立关联。用户指定牌号时优先核对该牌号；发现不匹配须说明，不悄悄换型号。
5. **写正文与单一 CTA。** 每封增加有用的新信息；只问本阶段最重要的一件事，避免反复索取已知信息。
6. **核对并保存。** 检查事实、主题、称呼、产品、附件、词数和签名，保存完整文件及状态，再给出文件链接与简短说明。

## 5. Mail Group 四封邮件

以下英文是结构模板，方括号是待填字段，不能直接作为可发送稿。实际交付必须替换全部占位符并加入第 7 节签名。

### Mail 1：建立认知

- 目标：说明联系原因，让客户知道我方与其业务的关联。
- 结构：一项客户业务事实 → 一句我方相关身份／供应业务 → 一个低门槛 CTA。
- 附件：无。
- 新建主题示例：`Malaysia TiO2 supply for [application]`。

```text
Hi [Name],

Your website lists [specific product/application]. I’m Ai Long with IKHLAS in Malaysia, supplying titanium dioxide for [relevant application].

What is your process for reviewing a new TiO2 supplier?
```

上面的 CTA 适合采购流程沟通。若不确定对方职责，改为询问合适联系人；若已确认其负责评估，可改为一项应用问题。只保留一个主要请求。

### Mail 2：建立信任并提出产品评估

- 目标：围绕具体应用，提出一个有资料依据的候选牌号。
- 结构：应用 → 候选牌号及理由 → 资料与评估条件 → 一个具体问题。
- 正文：不超过 90 词，不含主题、称呼、落款及完整签名。
- 新建主题示例：`Malaysia TiO2 [grade] for [application]`；真实回复沿用原主题。

```text
Hi [Name],

For [application], [grade] is a candidate for evaluation. Its TDS lists [documented property or recommended application].

I’ve attached the TDS for your initial review. Suitability would need to be checked in your formulation.

Which [single requirement] should we use for the initial comparison?
```

TDS 必须对应实际牌号与版本。REACH／TCC 等支持资料只在适用且可分享时附加，并按实际附件调整正文。没有附件时不得写 “I’ve attached”。仅有产品网页、尚无 TDS 时可以形成内部候选稿，标为“待技术资料复核”，不称已完成 TDS 核对。

### Mail 3：推动样品测试

- 目标：确认实验室评估的下一项条件。
- 前提：先检查客户回复及我方真实样品供应条件。
- 可确认事项：样品牌号、数量、费用、运输条件、实验室联系人；每封只选择当前最关键的一项。
- 不自行承诺免费样品、包运费或指定日期送达。

仅在样品供应已经确认时，可采用：

```text
Hi [Name],

A sample of [grade] is available for evaluation in [application].

What sample quantity does your standard lab evaluation require?
```

如供应尚未确认，先内部核实，或只询问客户测试要求，不写样品已经可供。客户未回复时，不称其已同意测试。

### Mail 4：按实际状态推进合作

| 实际状态 | 邮件内容 | 可选择的一项 CTA |
| --- | --- | --- |
| 已收到测试反馈 | 回应具体结果，提出有依据的下一步 | 确认一个复测或验收条件 |
| 客户要求报价 | 回答已确认的商务条件 | 补充一项关键缺失信息，例如数量或目的港 |
| 有兴趣但暂缓 | 说明已记录的安排 | 确认再次联系时间 |
| 连续未回复 | 简短确认业务相关性或正确入口 | 请求转介，或确认后续联系意愿，二选一 |

无回复且确有此前发送记录时，可采用：

```text
Hi [Name],

I’m following up on [grade/application].

Who is the right person to contact about TiO2 evaluation for this range?
```

跟进前检查新回复、退信、停止联系要求及承诺日期。收到回复后转为实际事项沟通；明确拒绝、不匹配、退信或要求停止时暂停并记录。发送间隔保持可配置，不预设固定天数，不因四封草稿齐备而自动排期或同时发送。

## 6. 产品、附件与词数复核

### 产品表述

- 牌号采用对应正式资料的拼写；历史候选型号不代表本次已确认适配。
- 引用数值时保留单位、测试方法及必要条件；不拼接不同牌号或版本的数据。
- 没有比较证据时，不声称“性能更好”“价格更低”“直接替代”或免测试适配；可用 `candidate for evaluation`。
- 价格、MOQ、包装、库存、交期、样品费用、生产地和原产地只写当前已确认信息；公司所在地不能自动证明货物原产地。
- 用户提供的固定签名按原文使用；其中的品牌或资质表述不自动扩展为某牌号、某批货或某进口主体的覆盖承诺。

### 附件台账

每个拟用附件记录：**原文件名｜对应牌号｜版本／日期｜用途｜适用市场及主体｜可分享状态｜草稿引用状态｜实际附加状态**。

TDS 核对版本及用途；REACH／TCC 核对出具主体、适用物质、覆盖对象、市场、日期及相关范围。没有核对依据时删除相应承诺并列待办，不把其他客户资料当成本客户凭证。

起草时只能记录“计划附加”或“文件已核对”；只有执行发送准备时确实附加完成，才能记录“已附加”。正文中的附件说明必须与最终发件内容一致。

产品链接须打开核对目标页面与牌号，清除误带标点。公司简介仅在对当前沟通有帮助时使用。

### 词数口径

- **正文词数**：只统计实际发给客户的英文正文；不含 Subject、称呼、Best regards 和签名。不计内部中文说明。
- **全封词数**：主题、称呼、正文、落款及签名文字合计，不计 To／From 等字段标签和收件地址字段。
- 统一按空白分隔词元计数；连续 URL、邮箱地址或连字符词各按一个词元计；若正文中有产品链接行，该行参与正文统计。
- Mail 2 必须重新统计并达到不超过 90 词；其他阶段保留实际词数，不在本版新增硬性上限。

### 资料不足时继续执行

| 缺口 | 可完成的工作 | 记录状态 |
| --- | --- | --- |
| 无完整 TDS／产品匹配不足 | 完成基于已核实业务的 Mail 1；Mail 2 列候选和技术待办 | Mail 1 按实际复核结果；Mail 2 待补资料 |
| 支持证书适用性未知 | 删除未支持的附件及覆盖承诺，保留可核实内容 | 单列资料缺口 |
| 主体、收件人或职责有关键矛盾 | 准备内部草稿及需要核实的问题 | 待补资料，不标可发送 |
| 发件通道未接入 | 完成正文、附件准备及文件保存 | 内容状态照实；发送状态待接入 |

## 8. 每次交付和文件保存

### 固定交付内容

1. **内部写作摘要**：客户、收件人、当前阶段、联系理由、主要 CTA、候选牌号及依据、待核实事项。
2. **每封完整英文稿**：From、To、Subject、称呼、正文、完整签名。收件人分别编写；不默认将同一公司其他联系人加入 Cc。
3. **附件清单与词数**：每封独立列出；中文说明与对外英文正文分开。
4. **复核与状态**：逐封判断，不能因 Mail 1 已复核就把 Mail 2 一并标为可发送。
5. **保存结果**：文件名、版本、日期及可打开的文件链接；未保存成功不能称交付已完成。

### 保存规则

- 格式：Markdown（`.md`）。
- 建议位置：对应市场的客户开发目录下“开发信”文件夹；如已有文件，更新原文件并保留版本历史，不因调整命名重复新建。
- 新建命名：`公司简称_联系人_Mail_1_2_起草日期.md`；单封使用 `Mail_1` 等阶段名称；同一收件人的多封可放一份文件，每封独立记录状态。
- 不同收件人分别保存；用户明确要求汇总时，可在一份文件中设独立收件人区块。
- 修改正文、签名或附件说明时，更新版本、更新时间及简短变更记录。已经发送的正文作为历史版本保留，不覆盖成新稿后仍称其为发送原文。
- 起草不上传至 GitHub 或其他外部渠道，除非对应任务已有明确的上传指令。

### 最小记录字段

客户 ID、公司、国家、收件人及邮箱、From／Reply-To、Mail 阶段、主题、正文版本、创建和更新日期、证据及完整链接、牌号与 TDS 版本、附件清单、正文及全封词数、复核结论、待办、发送授权、实际发送时间及结果、客户回复、下一步动作与计划日期。

将内容与发送状态分别记录，避免把“草稿已经写完”误记为邮件已发：

| 状态类别 | 可用值与含义 |
| --- | --- |
| 内容 | 待补资料／已起草／已复核待发送 |
| 发送 | 未发送／待接入／发送中／服务器已接受／已发送／部分失败／失败／结果待核实 |
| 跟进 | 未观察到回复／已回复／暂停／关闭；未查阅邮箱时明确写未核查 |

实际发送交给公司邮箱发送流程。明确获授权的指定邮件无需重复确认；关键项有歧义时只补齐缺项。SMTP 接受仅记录“服务器已接受”，不解释为已送达或已阅读；超时等不确定结果先核查，不直接重发。
