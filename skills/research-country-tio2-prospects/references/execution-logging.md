# 执行队列与逐次日志（本地补充规范 v1.1）

适用：本 Skill 在可运行 Python 的本地项目中执行市场搜集。依据仍为 SOP v1.2；本规范补充执行与记录机制，不改变基础核验、数量和预算规则。Python 3.10+，仅标准库，无账号或网络依赖。

## 执行顺序

1. 从当前完整候选池和检查点初始化日志中的队列，包含继承的全部五状态；`source` 写实际文件和检查点。首次空池也明确写“无历史线索”。同一任务续接已有日志，不能重新初始化或删日志重置队列。没有旧日志的历史批次，从当前时间开始记录，旧缺失仍标未记录。
2. 每次新发现动作前检查完整队列。pending 未清空，只允许为已登记公司补查或读取证据；不能将新公司搜索混在核验调用中。一个查询文本或一个页面目标对应一个动作，当前实现依次调用，不批量预发后续发现查询。10条查询仍可构成SOP中的一个完整轮，不要求一次并发。
3. 工具调用前用 `begin` 保存目标、目的、工具和关联ID，拿到 action_id 后才能调用；工具返回后立即 `end`，然后再判断事实、登记公司或开始下一动作。失败返回也必须闭合。新线索先 `lead` 为 pending/not_started，开始核验时更新为 in_progress；不得积压未登记的新线索后继续发现。
4. 每次返回读取/搜索结果后，以SOP判断公司状态并同步 `lead` 和候选总表；脚本不替代证据判断。不能为释放发现入口将未完成核验改成 unresolved。重启 unresolved 补查时先转 pending/in_progress，保留旧缺口。已 valid 的抽查失败按SOP判断降级。
5. 每轮开始、结束及正式交付前运行 `--check`，将 pending ID/阶段与总表逐条对齐，同时核对实际工具调用历史和日志。脚本只能检验已记录的队列和动作，不能发现漏登记的公司或拦截绕过它的浏览工具。
6. 每轮结束先更新、回读四份正式Markdown并保存报告检查点，再进入下一轮。达到目标转自检、切换核验/收尾轮也属于轮次切换；使用独立round_id，不能沿用旧轮次来绕过保存。每净新增约20家、暂停或最终交付也保存检查点，不等到全部搜索完成。

## 轮间正式报告检查点

脚本不代写研究结论。执行者按四文件模板更新当前已知内容：01同步全部状态；02补当轮证据；03更新实际动作、轮次与预算；04写阶段复核和未完成项。尚未自检就写“未开始”，证据不足就保留缺口，不能创建空报告充数。更新已有四文件前按项目约定保留history快照。

保存次序：

1. 结束当前调用并同步队列；运行`--check`取得`current_round`和`last_work_seq`。后者是当前研究进度所对应的日志序号，不是检查点事件的序号。
2. 将四报告更新到该进度并回读，确认ID、状态、证据、统计与工作表/日志一致。每份放入且仅放入一个版本标记，例如实际当前轮为R01、last_work_seq为27时：

   `<!-- research-checkpoint: {"round_id":"R01","through_seq":27} -->`

   不能只改标记而沿用旧内容。若初始化后尚无任何动作，阶段报告可用R00，明确无已执行动作及真实阻断。
3. 保存JSON输入`{"op":"checkpoint","round_id":"R01"}`，通过同一`--input`命令提交。脚本检查四文件存在、非空及标记对应当前进度，然后记录四文件SHA-256与覆盖序号；不会修改报告或凭空生成内容。
4. 下一轮`begin`若round_id改变，脚本要求报告检查点对应最新进度且四文件指纹仍一致。缺文件、旧标记、检查后改动或队列/动作继续变化，均须更新报告并重新checkpoint后才能换轮。状态仍有pending时允许保存真实阶段报告；保存成功不取消pending对发现的限制。
5. 自检结束后再次更新四报告并checkpoint，运行：

   `python -X utf8 skills/research-country-tio2-prospects/scripts/research_log.py --batch "<当前批次目录>" --check-reports`

   该检查同时要求已登记动作完整与报告版本对应最新进度。若仍有中断或未知项，应在阶段交付中披露返回码和缺口，不为得到0而改造事实。检查点保存后若补充报告正文，也要重新checkpoint；不要为写入“检查通过”的循环文字反复修改报告，可将最后检查结果另存工作文件。

兼容性：旧v1.0事件可继续只读检查，`--check`仍仅按日志是否闭合返回状态；新增`reports_current`不代表过去曾按时保存报告。`--check-reports`会指出旧批次未建立检查点，不倒填旧事件或改写旧报告冒充历史合规。明确续接旧批次时，从当前进度保存真实检查点后继续。

检查范围：脚本核对文件存在、标记与内容指纹，不能独立判断正文是否真实更新、证据是否充分。回读与工作表/日志对账仍由Agent负责；相同round_id内也不能故意延长一轮来绕过规定保存节点。

## 保存与调用

脚本：[research_log.py](../scripts/research_log.py)。日志：当前批次的 `logs/events.jsonl`，追加保存，包含初始化、状态变化、动作开始与结果；不可编辑旧行。不要存账号凭据、完整请求头或无关私人数据。

用文件工具保存 UTF-8 JSON 输入，再运行（将变量替换为本任务真实路径）：

```powershell
python -X utf8 skills/research-country-tio2-prospects/scripts/research_log.py --batch "<当前批次目录>" --input "<事件JSON路径>"
python -X utf8 skills/research-country-tio2-prospects/scripts/research_log.py --batch "<当前批次目录>" --check
```

输入可放在批次 `_work/`。脚本自动生成带 `+08:00` 时区的记录时间、连续序号和唯一 action_id；时间是日志写入时间，不能当工具内部开始/结束时间或有效研究耗时。

### 输入字段与例子

以下是格式示例，非真实研究动作。正式执行填真实内容，不把示例网址或公司写入业务日志。

初始化一次，`leads` 为当前完整队列。历史非pending的 `stage` 填 complete，表示继承其已有处理状态，不表示本轮重验：

```json
{"op":"init","source":"当前总表路径及检查点；完整队列已对齐","leads":[{"lead_id":"TEST-L001","status":"pending","stage":"not_started","reason":"目录发现，尚未核验"}]}
```

新增或更新一条状态，`reason` 指向实际证据、已执行步骤或尚未执行的缺口。新ID只接受 pending/not_started；已有ID可更新为五状态之一，pending 的阶段只能为 not_started/in_progress，其他状态为 complete：

```json
{"op":"lead","lead_id":"TEST-L001","status":"pending","stage":"in_progress","reason":"开始身份、官网、经营和业务核验"}
```

调用前登记。`kind` 为 search/read；`purpose` 为 discovery/verify；`target` 是一个完整实际查询文本或一个页面URL（PDF也按一次读取），`tool` 填实际工具名，`round_id` 为当前轮次。verify 的 `lead_ids` 必须含已登记ID，discovery 通常为 []：

```json
{"op":"begin","kind":"read","purpose":"verify","target":"https://example.invalid/company","tool":"实际页面工具名","round_id":"R01","lead_ids":["TEST-L001"]}
```

保存返回的真实 action_id。重试或替代入口另发 begin，分别增加 `parent_action_id`（前一次真实ID）及 `relation`（retry/alternative）；每次实际重试单独计数。新的核验搜索也归 verify，按SOP扣查询预算。

工具返回后登记。`refs` 为工具返回标识或真实证据文件位置；若工具没有稳定标识，立即将相关返回内容保存到本批次 `logs/evidence/`，引用该文件。只保存实际返回，不能把分析推断写成原始返回：

```json
{"op":"end","action_id":"使用begin返回的ID","outcome":"success","executed":true,"summary":"实际读到的事实及限制，不表示四项自动通过","refs":["实际工具返回标识或证据文件路径"],"error":""}
```

| outcome | executed | 必要记录 |
| --- | --- | --- |
| success | true | 实际结果摘要、至少一个refs；读到登录页/空壳页也如实注明，传输成功不等于证据通过 |
| error | true | 实际错误/失败现象，refs可为空；不能因为读取失败删除动作 |
| interrupted | true或null | 已确定调用但无完整返回用true；无法确认是否调用用null。summary/error说明中断及已知范围，不能虚构失败或成功 |
| cancelled | false | 确认仅登记了开始、实际未调用；说明取消原因，不能计作已执行查询 |

四种结果均须填写 summary、refs（列表）、error（无错误时空字符串）。开始记录只是调用意图；没有end不能推定已执行。中断后先检查实际工具历史，能找到返回则据实闭合；否则保留 interrupted，不补造过去时间。之后的重试用新的动作ID。

当前不支持修改已经end的结果。若已经用interrupted闭合，后来才找回原返回，在03/04追加核对说明及证据，保留脚本的历史未知/中断标记；不能再次end同一动作，也不能伪造一次新调用来补计数。报告分开写脚本计数和后来确认的差异，不宣称日志检查已完整。

## 检查结果与故障恢复

- `--check` 输出五状态统计、pending ID/阶段、未闭合动作、执行未知项、中断项、失败项、已确认执行的搜索和读取次数。已知失败有完整记录，可视为日志闭合；查询和读取的重试均分别计次。脚本不计算预算余额、不授予继续搜索权限，目标达成和SOP预算仍须检查。
- `discovery_allowed` 仅表示已登记队列无pending且无未闭合动作；它不是完整SOP继续许可。存在中断/未知执行时，先恢复可核查预算，无法确定则按SOP记录限制，不能凭该字段继续。
- 返回码：0为写入成功或所选检查通过；1为输入、队列/轮间报告门槛、文件/锁或日志损坏错误；2为检查发现未闭合、中断或执行未知记录，或`--check-reports`发现报告检查点缺失/过期。pending>0不必然是日志错误，需另按队列字段判断。
- 脚本失败时暂停下一次外部调用，保留返回及待保存记录，先修复记录能力；不得静默绕过。预算或工具已不允许继续时保存阶段结果，不为日志校验通过虚改状态。
- 同一批次仅一个写入者。`.writer.lock` 防止同时写入；若进程中断留下锁，先确认原执行者已结束、协调写入归属，再移走失效锁并记录恢复情况，不能抢占活跃任务。日志尾行损坏时保留原件，核对实际返回后恢复可验证部分并披露缺口，不自动丢弃坏行或重新初始化。
- 每轮在03报告记录日志路径、已确认次数、未知/中断项及与工具历史对账差异；04保留检查结论和限制。四份业务报告仍为正式成果，日志不是第五份客户名单。
- 记录完整性结论限于检查范围：自动检查通过不等于所有实际工具调用均已记录，也不证明证据真实或公司合格。每轮需结合工具历史对账，无法全部对账则写明缺口。


## 原始返回落盘检查

首个外部动作前先在本批_work中保存并回读一份本地测试文件，确认当前写入方式可用。真实返回先保存原文，再闭合动作；含引号的返回通过文件/结构化参数保存，不拼进会被shell重新解释的命令。返回保存失败时停止后续研究调用，先恢复实际返回的保存；无法找回则明确缺失及原动作，不补造，修复保存能力后才继续。每轮正式四报告仍按前述顺序更新，不以日志代替。
