# 公司组织结构与联系人邮箱

依据《公司组织结构与联系人邮箱获取 SOP V1.0》及用户2026-10-21、2026-10-22规则，承接背调，为后续开发信准备联系对象、选择理由、沟通切入点和联系渠道。技能流程V1.5（本地适配）：每家公司累计最多3位具名工作邮箱联系人、本联系人流程Apollo总消耗最多3 credits，自动选人；付费邮箱队列须有原始搜索has_email=true证据；取消技能候选审批，工具的费用确认按其当前要求执行。默认中文交付，保留英文原始名称与职位。完整读取本文件和[报告字段与模板](references/report-contract.md)，按真实阶段续接，不从头重复已完成步骤。

项目本地执行还须读取[批次与预算规范](references/local-batch.md)；单公司任务建立单项批次，同样使用持久公司账本。写批次文件前读[批次模板](assets/batch-templates.md)。整个Skill的§0—§6和两份报告规范均适用；Agent只增加批次调度，不以角色摘要替代本Skill。源导入和本地差异见项目[验证记录](../../docs/agent-team/company-contacts-validation.md)。

## 0. 每家公司最多3位，默认自动执行

- 将用户2026-10-21指令“每一家公司获取联系人邮箱不要超过3个。同时不需要我审批了”作为本技能的持续业务授权：自动筛选最相关人员，在限额内获取工作邮箱并保存两份报告，不再设置技能自身的候选审批关卡。
- 按同一客户/公司累计去重计数，不按批次、会话、文件日期、域名别名或新旧名称重置。先读已有邮箱记录；历史已选或已付费获取的人占名额；仅背调收集但未选用的公开人员和邮箱不占名额，不因公开线索超过3人停止本阶段选人，同一人更新/复验不新增名额。每人保留一个首选工作邮箱，不主动获取多地址。公共info/sales等部门邮箱单列，不计具名联系人名额。
- 计算剩余名额=max(0,3-历史已选或已付费获取的具名联系人数量)，新增选中人数不超过剩余名额；已有2位则最多再取1位。已有3位或以上时停止新增，保留历史记录，不删除旧证据或虚报为3位。
- 自动优先选择合适的采购和管理人员；两类都没有合适人选时才选择技术和销售。第一组只有1—2位时按实际人数交付，不用第二组补满3位。结合公司类型、实际职能、主体归属及现职证据判断；管理职位不等于采购权，销售可作转介入口，不标成已确认采购人。
- 人员适合联系与具备邮箱获取条件分别判断。完整组织台账保留所有相关人员；固定付费队列仅从符合上述岗位、归属及现职要求且本会话原始搜索返回`has_email=true`（布尔值）的人中选择。false、null、字段缺失或未知均保留为线索，默认不付费enrichment；职位重要、预算有余或已获费用批准均不能替代邮箱依据。采购/管理有人但均无邮箱，不等于两类无合适人选，不因此转选技术/销售。
- 每公司本流程Apollo总上限3 credits，包含公司查询、公司enrichment、人员enrichment、复验和收费重试。沿用同一公司持久账本，跨批次/会话/别名不重置。调用前核对已耗＋未结算最大预留＋本次最大费用≤3；费用或执行未知先对账，不按0释放额度。具体预留与恢复按本地规范执行。
- 本次新人的尝试范围也限制为剩余名额：选定后不因无邮箱、未匹配或失败而无限更换候选。返回不足3位可直接交付，记录缺口，不伪造结果；今后任务再次检查公司累计计数与历史尝试。
- 用户明确选择超过剩余名额时，在限额内按其明确优先顺序选择；未给优先顺序则按岗位相关性选择并说明，不暂停要求重新审批。只有用户明确修改上限才改变3位规则。
- **工具规则单独适用：** 持续业务授权不代替工具强制要求的具体人数、费用与明确确认。工具允许预授权时直接执行；工具仍强制逐次确认时，先完成自动选人、精确范围/费用披露及两份阶段文件，只请求一次工具要求的确认，明确说明限制来自工具，而不是本技能。已有满足工具要求的确认不重复询问。不得改用其他工具或手段规避同一确认限制。

## 1. 识别对象与阶段

- 读取目标公司最新背调及已有组织结构、联系人邮箱文件。沿用客户ID、经确认官网、项目目录、历史人员记录和候选编号；未知内容写明缺口。
- 直接承接背调中的公司业务、公开人员、职位、联系方式及来源日期；已有可信证据可复用，不为换阶段重新调查。影响主体识别或选人的矛盾再针对性核实；保留继承来源，不称本次重新核验。
- “下一家”按当前人员发掘名单与完成记录定位，排除已完成和用户跳过的公司；不要用背调进度冒充联系人进度。无法唯一定位时先整理已知进度，再问一个必要问题。
- “获取1，2”等选择映射到最近明确候选表的人员ID，并检查公司累计3位上限。已有满足工具要求的确认直接执行，不重复确认；编号无法唯一对应时澄清身份，不借澄清重新设置业务审批。
- 没有背调时先查找。确实缺失则报告，并完成足以区分主体的最小官网核查；不要宣称已做完整OGLD背调。独立完整背调交由 research-customer-ogld。
- 公司名、品牌、国家或官网冲突未解时，不混合公司人员，不进入付费获取。

## 2. 匹配公司并检索整体人员

- Apollo是主要人员工具。发现并读取执行时的公司匹配、人员搜索、Profile及Enrichment工具说明；以当时参数、费用和确认规则为准。不要硬编码案例域名、余额、人数、人员ID或价格。
- 以已确认域名、名称、国家及业务匹配公司；组织ID可用则记录。只有域名人员搜索可用时注明主体匹配限制。
- 首轮不加采购或技术职位筛选。处理分页至接口已知结果取完；记录参数、日期、每页数、页码、total及限制。受限则交付明确范围内的结果，不称全体员工。
- 按人员ID去重，记录原始数与唯一人员数。无ID时谨慎比对，多义记录保留。关联公司、海外分支、渠道分别标注，共享域名不证明同一法律或采购主体。
- 再检查采购、技术研发、生产运营、质量和管理岗位缺口，必要时用职位同义词、公司别名、已确认关联主体定向补查。记录查询及停止原因；宽泛关键词噪声不纳入目标公司统计。
- 保留搜索中的遮挡姓名、职位、has_email、更新时间、来源及未返回字段；不要为补全姓名提前Enrichment。

## 3. 建立组织结构并保存阶段成果

- 组织调查用于理解职责和选择联系对象。完成已知检索范围、必要缺口补查和证据整理后即可交付；不以补齐所有部门、人员或整张组织图为完成条件。
- 同时呈现三层：公司/关联主体关系；全量人员与职能分布；有证据的管理或汇报关系。按模板保留完整台账，不能只列拟联系的两三个人。
- 将法定董事、经营岗位、平台职能分类与实际部门分别描述。职位层级不证明汇报关系；只有来源明确时画组织图，否则用表格。
- 关键职能缺失写“本次未检出”，不写“公司没有”。渠道、异常及疑似历史人员保留在单独分类，不计为已确认员工。
- 官网、登记资料和公开职业资料用于必要核查。记录完整网址、查询日期、证据状态；区分搜索摘要、已读正文和继承背调。PDF读取失败不称全文核验。
- 并列记录职位/简介/任职日期冲突。current=true、更新时间、平台组织归属均不等于独立现职核验；不臆测晋升日期或采购权限。
- 自动选人后推进邮箱获取并保存两份结果。若被工具强制确认阻挡，先保存组织结构文件及邮箱阶段文件，状态写“等待工具强制确认”；已有真实内容必须完整保存，不回到“等待用户选候选”。

## 4. 自动筛选并固定执行范围

- 先评估采购和管理入口；两类均无合适人选才评估技术和销售，记录第一组核查依据。其他职能仍保留在完整组织台账，邮箱选择遵循第0节的累计上限和优先顺序。
- 再做邮箱准入：在允许的岗位组内筛出`has_email=true`并核对同一Apollo ID的原始搜索证据，从中排序选择最多剩余名额/预算允许的人数。仅将实际拟付费者写入`selection.people`，附`has_email:true`及`email_evidence={path,sha256}`；原始返回文件保留到批次evidence目录。false/未知者在两报告标为“仅组织线索：无邮箱/可用性未知，未调用”，不占本轮固定付费范围，不写成enrichment失败。没有符合者时队列为空，不为凑数获取。
- 分别统计岗位相关候选人数、其中邮箱可用人数、固定付费人数；工具费用确认中的N仅为固定付费人数，不使用全部相关候选数。`has_email=true`是准入条件，不保证返回具名工作邮箱或实际可投递。
- 给候选固定编号，映射台账编号及原搜索ID；记录原始职位、价值、职责疑点、has_email、优先级和选中/未选原因。选定后不重排编号对应的人；完整候选可以超过3位，但实际获取遵守名额限制。
- 为推荐联系的对象各整理简短选择理由和沟通切入点：从背调中取与其职责相关的业务事实，写清为何联系及可沟通的一件具体事项，并引用事实来源。按职责推断的联系价值在原句中注明；不把未知需求或采购权写成事实。此处提供写信依据，正文、产品选择及表达由开发信阶段处理。
- 推荐联系对象与固定付费队列分开：背调已确认的公开人员即使无Apollo ID或has_email非true，也可按岗位优先级整理四项交接材料，联系渠道如实注明。这不使其进入selection.people、不新增付费许可；仅有公共部门/公司入口时按入口交接，不杜撰收件人或将公共邮箱归给某个人。
- 普通采购不等于负责TiO₂，Technical Support不等于研发，董事不等于采购决策人。未知TiO₂需求时先确认用途、采购主体及职责，不凭职位推荐牌号。
- 执行前记录已有具名邮箱人数、剩余名额、本次新增及复验人数、预计获取后累计数，按当前工具规则查询余额、计算实际拟调用人数与费用；同时核对公司3-credit账本。复验也可能收费，不能将剩余名额直接当作调用人数。整批任务先逐家完成本节及阶段保存，汇总全部固定选中人员和费用，再办理工具要求的全范围确认。
- 默认使用持续业务授权自动执行，不再要求用户逐个批准候选。如工具强制确认，披露的范围只能是自动选定的本次名单，不是所有备选人；使用工具要求的原文，确认一次后完成。余额或强制前提缺失时真实记录。
- 历史个人邮箱与公共邮箱分列来源/日期；历史具名联系人计入上限，公共邮箱不冒充个人采购联系人。无法判断是否同一公司或同一人时先核实，不通过重复归类扩大名额。

## 5. 仅获取限额内选定人员的工作邮箱

- 优先传本会话人员搜索实际返回的ID，遵守工具对ID来源的限制；不可从案例、技能、历史会话记忆猜用ID。若跨会话只有存档ID而工具禁止复用，重新搜索并核对同一人后使用；核对原选定对象，不用新匹配偷换固定编号。
- 调用前重新核对本会话ID、`has_email=true`和原始证据指纹，并运行批次检查器。跨会话重搜变为false/未知时保留旧批准及候选映射，暂停该人的新付费请求，不自动换人。历史邮箱直接复用不收费；付费复验同样适用准入条件。已完成的旧调用只保留事实与消耗，不倒改标记、批准或费用以通过新规则。
- 每批只含限额内选定人员，满足工具适用的授权要求；关闭个人邮箱和电话揭示。批次拆分不改变公司累计3位上限，也不绕过工具总费用/人数确认。
- 按返回ID映射人，不按数组顺序。核对公司、域名、姓名及职位，保留原遮挡值与新全名。
- 记录email、email_status、match_confidence、catch-all及verdict、任职/组织字段、LinkedIn、日期和请求ID；缺失写“未返回”。保留请求ID字符串避免数字精度损失。
- 分别统计请求数、匹配数、有/无邮箱数、失败数及实际credits。has_email、返回邮箱、verified、catch-all、实际投递是不同状态；verified不保证可达。
- 匹配成功无邮箱、未匹配、接口失败、未选中、达到上限、工具确认未满足分别记录。超时状态不明先检查结果或请求状态，禁止盲目重试重复付费；按接口要求反馈异常。不得因失败自动扩充本次新人尝试范围；需要新增工具确认时说明实际费用与范围变化。
- 组织文件同步新全名、职位、组织证据、累计人数与执行状态；保留旧证据及冲突。获取邮箱不授权发送邮件。

## 6. 保存、核对、交接

- 按模板分别保存 `{公司英文名}_组织结构_{YYYY-MM-DD}.md` 与 `{公司英文名}_联系人邮箱_{YYYY-MM-DD}.md`，空格替换下划线，日期使用北京时间。
- 与对应背调放在同一公司目录，使用本地文件工具保存，替代原Library步骤。更新前保存history快照；同次补充沿用原路径和首次日期，增加更新时间与变化范围。公司持久预算账本在contacts/ledger.json，批次目录、检查点及检查命令见本地规范。
- 联系人邮箱报告的简短元信息之后，按report-contract的“人员详情与交接（开发信准备）”逐对象交付四项材料；组织报告引用此处，调查明细、邮箱执行与费用记录列在后面。不另增“使用边界”栏目，必要的不确定信息写在对应项中。
- 交付前逐项核对：联系对象及来源可定位，选择理由对应职责，沟通切入点对应已有业务证据，联系渠道及验证状态与实际记录一致。确实未取得的内容写具体缺项；无适合个人时交付公共入口，连入口也未取得则明确缺少对象/渠道。已有材料可以阶段交付，不用编造内容凑齐四项。
- 必要调查已完成、来源及账目已核对后，个人邮箱缺失或组织图不完整本身不阻止结束本轮处理，不为此无限补查。主体冲突、必要工作未完成、工具确认未满足或费用未知仍按本地规范保留真实状态；交接材料存在不等于已具备发送条件，也不自动放行被阻塞的公司。
- 核对公司累计具名邮箱人数≤3（已有历史超限单列，不新增）、本次新增/复验人数、候选-ID映射、仅选定人被获取、字段原值、冲突、完整来源网址、两份文件状态一致。成功保存后才宣布完成；失败逐份说明。
- 最终简要展示四项材料的入口及联系人/渠道缺项、实际/预留/未知费用，并提供两个真实文件链接。独立单公司任务止于本公司；明确的批次任务由Agent在阶段保存并检查后连续处理下一家，不逐家要求用户续行。只请求工具真正要求且尚未满足的费用确认。不会自动起草或发送邮件。

## 常见偏差

| 可见情况 | 应执行的处理 |
| --- | --- |
| 搜索返回很多销售，没有采购 | 保存完整范围，定向补查关键职能，说明缺口 |
| 只有候选名单、没有组织文件 | 补齐主体关系、职能表和全量人员台账再交付 |
| 默认无需候选审批 | 自动选人并推进；仅在工具强制要求时做一次具体确认 |
| 公司已有2位具名邮箱联系人 | 新人最多1位；不得每轮再增加3位 |
| 公司已有3位或更多 | 停止新增并保留历史；不通过改域名/日期重置名额 |
| 用户已满足工具人数/费用确认 | 在公司名额范围内直接执行，不重复确认 |
| verified与catch-all同时为真 | 同时记录，不承诺投递成功 |
| 拿旧邮箱再次提交结果 | 标明历史来源；只有本次实际返回才能记本轮获取 |
